# CLI с записью действий и анализом LLM

Интеграция выполнена на основе `origin/dev` (рабочая ветка `audit-integration`).
Здесь уже реализовано создание VM через API, соответствующее вашему конфигу.
Переключаться на `master` для запуска не нужно: там осталась старая заглушка.

## Запуск

Все команды выполняются из `tui-ansible-runner`. Локально нужны Go 1.26,
OpenSSH, Git с доступом к репозиториям упражнений и audit-agent, Python 3.10+
для анализа LLM. Соседний каталог `audit-agent` не нужен: исходники скачиваются
при подготовке агента из настроенного Git-репозитория в локальный кеш.
На каждом запуске подготовки получается указанный `ref`; одна ревизия
используется до конца текущего процесса CLI. Можно закрепить commit SHA.

Сохраните ваш конфиг с `exercise_repository` и `vm_service` в `incidentctl.json`.
Он совпадает с `incidentctl.example.json`. Поля `image_id` и `ttl_seconds`
сохраняются в существующем API-потоке; менять их для audit не требуется.

Windows PowerShell:

```powershell
# Если incidentctl.json ещё не создан:
Copy-Item incidentctl.example.json incidentctl.json
go build -o bin/incidentctl.exe ./cmd/incidentctl
.\bin\incidentctl.exe -config incidentctl.json
```

Linux/macOS:

```bash
cp incidentctl.example.json incidentctl.json  # только при отсутствии своего конфига
go build -o bin/incidentctl ./cmd/incidentctl
bin/incidentctl -config incidentctl.json
```

В TUI нажмите `a` и введите пользовательский токен VM API. Он сохраняется
в системном каталоге конфигурации рядом с `user-id`; API-ключ LLM вводить здесь
не нужно. Существующая реализация получает VM-токен из этого файла,
поле `token_env` в конфиге не включает чтение переменной окружения.

Выберите упражнение, откройте описание (`Enter`) и начните решение (`s`).
CLI создаст VM через `https://petruekhin.tech:19453`, получит SSH-реквизиты,
подготовит Ansible и audit-agent, выполнит `infra`, `incident` и контрольную
verification-проверку ожидаемой ошибки. Затем он вызовет
`incident-audit start --session-id <новый ID>` и только после успешного старта
получит и откроет ссылку веб-терминала. В списке этапов видны установка агента
и начало записи. При сбое записи терминал не открывается.

При установлении SSH-соединения выполняются до трёх попыток подключения;
сам удалённый playbook при этом повторно не запускается. Если связь прервалась
на этапе проверки воспроизведения инцидента, клавиша `p` повторяет этот этап
на той же VM, предварительно получив актуальные SSH-реквизиты из API.
Создание VM, `infra` и `incident` при этом не повторяются. Постоянная ошибка
связи блокирует переход к записи и терминалу и явно показывается как ошибка SSH.

Целевая VM должна быть Ubuntu/Debian x86_64 с systemd, Python 3.10+,
ядром с `CONFIG_AUDIT`/`CONFIG_AUDITSYSCALL` и доступом к APT. Установщик
агента сам ставит `auditd` и `python3-audit` и проверяет поддержку audit.
Существующий bootstrap/playbook-поток предполагает root SSH-доступ.
Для управления агентом поддерживается и `sudo -n`.

## Проверка решения

На экране решения нажмите `v`. CLI сначала вызывает `incident-audit stop`
с ID этой попытки. При ошибке stop или экспорта проверка блокируется.
Только после успешной остановки выполняются загрузка упражнения и Ansible
verification — их действия не входят в запись пользователя.

Локально создаётся новый каталог `analysis/<exercise>-<unique>/`:

- `llm.json` — компактный пакет действий;
- `validation.json` — результат и полный вывод Ansible;
- `task.md` — контекст задачи при запуске LLM-анализа.

Каталог для итоговых LLM-отчётов задаётся в `incidentctl.json`:

```json
"audit": {
  "llm_reports_dir": "llm-reports"
}
```

Можно указать абсолютный путь или путь с `~`. Относительный путь считается
от каталога `incidentctl.json`. По умолчанию используется `llm-reports` рядом
с конфигом. Отчёты сохраняются как `<каталог>/<название задачи>/<номер решения>/analysis.md`
и `analysis.json`, например `llm-reports/nginx-wrong-api/1/analysis.md`.
Markdown содержит учебный постмортем: результат и влияние, ключевые события,
причину сбоя, подтверждённые действия, приведшие к исправлению, улучшения
диагностики, меры предотвращения повторения и ограничения доступных данных.
Существенные выводы привязаны к ID действий; недоказанные причины и эффекты
отмечаются как гипотезы. Имя файла `analysis.md` сохранено.
Нумерация начинается с 1 отдельно для каждой задачи и продолжается после
перезапуска CLI; существующие отчёты не перезаписываются. Неуспешная
Ansible-проверка не занимает номер. Если после успешной проверки LLM-анализ
завершился ошибкой, его номер сохраняется, следующий запуск получит новый.
Старые отчёты из `analysis/` автоматически не переносятся.

Полные журналы остаются на VM в `/var/log/incidentsim/sessions/<session-id>/`.
ID попытки хранится в `<remote_work_dir>/.audit/attempt.json`, поэтому повторная
проверка и другой процесс CLI могут использовать ту же закрытую запись.
Для одной VM используйте один `remote_work_dir` и выполняйте операции последовательно.

Сразу после завершения Ansible-проверки запись автоматически включается с новым
ID независимо от результата, до сохранения отчёта и обращения к LLM.
Можно продолжать работу в терминале без отдельной кнопки. Сохранённый пакет
завершённой попытки не изменяется. Если запись включить не удалось, CLI явно
показывает ошибку. Выход из TUI оставляет VM и запись работающими до следующей
проверки/закрытия или завершения самой VM.

## LLM

Все настройки агента и DeepSeek задаются в `incidentctl.json`:

```json
"audit": {
  "repository": {
    "repository": "git@github.com:IncidentSim/audit-agent.git",
    "ref": "main",
    "subdirectory": ".",
    "cache_dir": "~/.cache/incidentctl/audit-agent"
  },
  "llm_reports_dir": "llm-reports",
  "llm": {
    "enabled": true,
    "api_key": "YOUR_DEEPSEEK_API_KEY",
    "api_key_env": "DEEPSEEK_API_KEY",
    "base_url": "https://api.deepseek.com",
    "model": "deepseek-flash",
    "timeout_seconds": 120,
    "max_tokens": 4000,
    "proxy_mode": "direct"
  }
}
```

После этого достаточно `make run`. Git использует обычные SSH-ключи и настройки
вашего компьютера; при необходимости замените SSH-host на свой alias либо
укажите HTTPS URL. Нужен доступ к репозиторию. Ошибка скачивания показывается
на этапе установки агента. Относительный `cache_dir` считается от каталога
конфига; `~` поддерживается. Старые ревизии кеша не удаляются автоматически.

`api_key` из JSON имеет приоритет; если он пуст, используется переменная
из `api_key_env`. Ключ не записывается в Git-кеш или временный профиль и не
передаётся на VM: он передаётся через окружение только локальному процессу
анализа. Локальный `incidentctl.json` исключён из Git. Пример содержит пустой
ключ. Для отключения LLM установите `audit.llm.enabled: false`.

Промпт постмортема встроен в TUI. `proxy_mode: direct` отключает прокси только
для процесса анализа; `environment` использует системные настройки.

Для совместимости сохранены внешний профиль `audit.llm_config` и флаг
`-audit-llm-config`: явно переданный флаг имеет приоритет над секцией `llm`.
Пустой `-audit-llm-config=` отключает анализ. При использовании внешнего
профиля действуют заданные в нём пути к ключу и промпту.

```powershell
make run
```

Linux/macOS:

```bash
make run
```

При `v` после остановки и Ansible-проверки локальный клиент отправляет
компактный пакет, README упражнения и результат verification в настроенную
модель только если verification завершилась успешно. Если решение ещё не прошло
Ansible-проверку или произошла техническая ошибка, LLM не вызывается;
сохраняются только логи и результат проверки. Путь к отчёту показывается
в выводе CLI/TUI. Если LLM недоступна, ключ отсутствует или клиент не запустился,
CLI показывает предупреждение «Проверка с помощью LLM не удалась» и использует
результат Ansible-проверки. Ansible выполняется один раз до запроса к модели,
так как его результат входит в запрос. Ошибка LLM не превращает успешную
Ansible-проверку в ошибку и не скрывает неуспешную. Предупреждение остаётся
в статусе TUI; логи сохраняются. Ответ модели не меняет результат
Ansible-проверки. Каждый успешный verify с LLM-флагом делает новый запрос;
автоматических повторов платного запроса нет.

Python-клиент LLM запускается на компьютере с CLI. При запуске из PowerShell
это ваш Windows-компьютер. Именно ему нужны LLM-профиль, API-ключ и доступ к сети;
хост Firecracker и пользовательская VM ключ не получают. VM API-токен из TUI
и API-ключ LLM — разные учётные данные для разных сервисов.

Дополнительные флаги: `-audit-agent-dir ../audit-agent`, `-audit-python python`
(`python3` по умолчанию вне Windows), `-audit-reports-dir analysis`.
Все эти пути считаются относительно текущего рабочего каталога.

## Команды без TUI

Для существующей VM используйте `-vm-id`: CLI получает её SSH-реквизиты и
временный ключ через тот же API. VM ID показывается в выводе подготовки решения;
также его можно получить через API. Токен должен быть заранее сохранён через TUI.

```bash
bin/incidentctl -vm-id VM_ID verify nginx-wrong-api
bin/incidentctl -vm-id VM_ID ssh-check
```

`infra` и `incident` также принимают `-vm-id`. Они закрывают прежнюю запись до
изменений и начинают новую после успешного playbook. TUI создаёт одну запись
после всех подготовительных этапов. Повторный `verify` использует
новую запись, автоматически открытую после предыдущей проверки.
