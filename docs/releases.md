# Сборка и публикация дистрибутивов

Пользователь скачивает архив из GitHub Releases. Внутри ровно три файла:
`incidentctl` (на Windows — `incidentctl.exe`), пользовательский `README.md`
из `distribution/README.md` и `incidentctl.example.json`. Рабочая конфигурация,
токены, ключи, кеши и журналы в архив не включаются.

## Локальная сборка

Нужны Go из `go.mod`, Git и доступ к GitHub. Из корня только этого репозитория:

```bash
make release VERSION=v0.1.0
# Без Make, в том числе в PowerShell:
go run ./tools/release -version v0.1.0
```

Команда создаёт `dist/v0.1.0/`:

- `incidentctl_v0.1.0_windows_amd64.zip`;
- `incidentctl_v0.1.0_linux_amd64.tar.gz`;
- `incidentctl_v0.1.0_darwin_amd64.tar.gz`;
- `incidentctl_v0.1.0_darwin_arm64.tar.gz`;
- `SHA256SUMS` и `build-info.json`.

Готовый каталог не перезаписывается: для новой сборки задайте другую версию
или новый каталог через `-output`. Для проверки одного варианта:

```bash
go run ./tools/release -version v0.1.0-rc.1 -targets windows/amd64
```

Сборщик один раз получает актуальную `main` audit-agent и использует её
для всех платформ. `AUDIT_AGENT_DIR`, `AUDIT_AGENT_REPOSITORY`, `AUDIT_AGENT_REF`
позволяют выбрать другой источник, как при обычной сборке.
В каждый TUI включены только Linux amd64 агент для VM и агент для соответствующей
локальной платформы. Сборка идёт в отдельном временном каталоге: локальные
бинарники из других сборок не попадут в дистрибутив.

`--version` показывает версию TUI и ревизии TUI/агента. `build-info.json`
содержит те же ревизии и версию Go; `-dirty` означает локальные изменения
в исходниках. Ревизия агента записывается для диагностики, сборка по-прежнему
получает текущую ветку, а не закреплённый коммит.

## Автоматическая публикация

После отправки workflow и исходников в GitHub создайте тег на нужном коммите:

```bash
git tag -a v0.1.0 -m "incidentctl v0.1.0"
git push origin v0.1.0
```

Workflow `.github/workflows/release.yml`:

1. Проверяет тег, запускает Go-тесты и `go vet` на Linux.
2. Собирает четыре архива с одним checkout audit-agent.
3. Запускает готовые бинарники на Windows, Linux и обеих архитектурах macOS.
   Версия проверяется без Go/Git/SSH в `PATH` и без пользовательского конфига.
4. После успешных проверок публикует архивы, метаданные и контрольные суммы
   в GitHub Release с автоматически сформированным описанием.

Тег с суффиксом, например `v0.1.0-rc.1`, создаёт prerelease. Можно также
запустить workflow вручную в Actions → Release → Run workflow, указав
**существующий** тег. Секрет вручную добавлять не нужно: публикация использует
`GITHUB_TOKEN` с `contents: write` только в job публикации. Политика организации
должна разрешать выполнение Actions и эту запись в репозиторий.

При ошибке загрузки можно перезапустить workflow для оставшегося draft-релиза.
Уже опубликованный релиз не перезаписывается. Новая версия audit-agent попадает
к пользователям после выпуска нового TUI с новым тегом.

Подпись Developer ID и нотариализация macOS в этот workflow не включены.
Релизный архив сопровождается пользовательской инструкцией, а архитектура
и команды для разработчиков остаются в корневом README.
